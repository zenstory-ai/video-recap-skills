# Agent Note: 故事索引的剧情时间与重复角色做确定性修复

Status: implemented

## Problem

`consolidate.py` Pass B 由模型写出 `understanding_index.json`，真实运行里有两类稳定出现的瑕疵：

- `plot_points[*].time` 出现秒数 ≥ 60 的 `mm:ss`，如 `00:95`：模型把场景的秒数直接填进了秒位。写稿 Agent 按这个时间去找画面会找错。
- 同一个角色被拆成两条 `characters`，彼此共享名字或别名（一条叫"范闲"，另一条叫"小范大人"、别名里有"范闲"），关系也随之分裂成两条，brief 的 Characters 段重复列人。

## Decision

- 新模块 `skills/video-understanding/scripts/index_normalize.py`（纯函数，无 I/O）：
  - `parse_plot_time` 读 `MM:SS` / `H:MM:SS` / 裸数字 / `12.5s` / `12.5秒`，全角冒号（`00：95`）当半角读，`3分20秒` / `3分钟` / `1小时2分3秒` 这类中文分秒写法先改写成冒号形式再读，`1.5分` / `2.5分钟` 这类小数分钟按分×60 读，`第3分钟` / `第95秒` 去掉序数词"第"后读（`第3分钟` 读作 `03:00`）（序数单位后来改为读该单位的起点，`第3分钟` 读作 `02:00`，见 `2026-10-03-ordinal-plot-time-reads-unit-start.md`），去掉开头的"约""大约"和任意位置的"左右""前后""许"（`01:20左右`、`3分钟前后`、`80秒许`），区间（`01:20-01:45`、`01:20至01:45` 等）取起点，各字段不做范围检查，`00:95` 读作 95 秒、`1:75` 读作 135 秒；`format_plot_time` 写回规范的 `MM:SS`（超过一小时写 `H:MM:SS`）。读不出来、为负、或超过已分析场景末尾 1 秒以上的时间直接删掉 `time` 键，剧情文本和顺序保留。字符串形式的剧情节点原样通过。
  - `merge_characters` 按名字（去空白、不区分大小写）判断同一人，结果与输入顺序无关。`aliases` 写成字符串时当作一个别名（`parse_index_response` 与 `normalize_index` 都把它改成列表），不会被拆成单字。步骤：
    1. 同名条目先归为一个节点，别名取并集（同名就是同一人被拆开，不再单独判断）；没有名字的条目各自成节点。
    2. 节点两两判断是否相连：一个的名字等于另一个的某个别名即相连；两者只共享一个别名（如都带"男子""老板"）不相连。
    3. 一个节点的相连节点里有两个彼此不相连时，它是桥（两人都带别名"男子"、另有一条名叫"男子"的路人；或一条 `{丙, aliases [甲, 乙]}` 同时点名甲、乙两人），桥单独保留、不参与合并，也不把两边并成一个。
    4. 其余节点沿相连关系取并集。每组在第一个成员的位置输出，保留组内第一个有名字的成员的名字（第一个成员没有名字、只靠别名连进来时，名字取自后面的成员，不会留下无名角色、也不会把关系改指成空），其他成员的名字进 `aliases`；`aliases` / `visual_descriptions` / `asr_mentions` / `evidence_ids` 稳定去重合并，`description` / `research_role` 取第一个非空值，`confidence` 取较高者。
    分组只由节点之间的关系决定，同一份条目换任何顺序得到同样的划分（输出的名字和字段顺序跟着第一个成员走）；对已修复的索引再跑一遍不再合并。
  - `repoint_relationships` 把关系两端改指存活的名字，丢掉因合并产生的自环（"范闲—同一人—小范大人"），同 `(a, b, relation)` 的重复关系合并 `evidence_ids`。
- `consolidate_index` 在确定性 ASR/调研兜底之后调 `normalize_index`，时长上限取 `vlm_analysis` 的最大 `end`；有修复时记一条日志。缓存命中时也跑一遍：旧版本写下的索引若有变化，就地改写 json/md/meta，不再调模型。修复是幂等的，已规范的索引不会被重写。brief 的索引读取（`briefing/context._load_consolidation`）也跑一遍 `normalize_index`，所以 `--brief-only`（cut 第二轮、素材库恢复）不用等下一次完整理解；这里不传时长上限，因为 brief 的场景可能是剪辑后的时间线，而剧情时间是原片时间。
- 测试：`tests/understanding/test_consolidate.py` 覆盖各种时间写法（含"约"、"秒"、区间）、不可读与越界时间、名字即别名的合并与关系重指、无名条目排在前或后都取有名成员的名字且关系不改指成空、连到两组的条目单独保留（含两人共享别名"男子"再加一条名叫"男子"的条目，三人与关系都保留）、同名条目先合并再判断相连、两组桥接夹具（"王大锤/李警官/男子"与"丙[甲,乙]/甲/乙"）的全部排列得到同一划分且关系保留、只共享别名不合并、字符串别名不拆字、幂等，以及缓存命中时修复旧索引且不调模型；`test_consolidation_brief.py` 覆盖 brief 读取时修复拆开的旧索引。

## Alternatives considered

- **在 `INDEX_PROMPT` 里要求秒位 < 60、同一角色只出一条。** 最强理由：从源头减少瑕疵。没采用：prompt 写在索引 meta 里，改一个字就让所有已有索引重建一次（每个 work_dir 多一次付费调用），而模型仍可能不遵守；确定性修复对新旧索引都有效。
- **秒位 ≥ 60 时判为无效直接丢弃。** 最强理由：不猜模型的意图。没采用：真实样本里这类时间就是场景秒数，进位后和场景时间对得上；猜错的风险由场景末尾上限兜住。
- **按输入顺序逐条归组（每条只看已形成的组）。** 最强理由：实现简单，一次遍历，"已有组 + 新条目"的判断直观。没采用：结果取决于条目顺序。路人"男子"排在两位主角之间时，它先并进第一位主角，第二位主角再通过名字"男子"连进同一组，两人被并成一个、两人之间的关系被当作自环删掉；`[{丙, aliases [甲,乙]}, {甲}, {乙}]` 这个顺序也会把三条并成丙。模型输出的条目顺序没有保证，同一份内容不能因为顺序不同得到不同的角色表。
- **严格按原始条目建图，同名条目也可能被判为桥。** 最强理由：完全照搬"名字相同即相连"的两两规则，不需要先归并同名。没采用：两条同名"男子"若同时连着两位主角，会各自成为桥，输出里留下两条同名角色；同名本来就是同一人被拆开，先归为一个节点再判断更符合数据，输出的名字也不会重复。
- **合并时让信息更多的条目当主条目。** 最强理由：留下更好的名字。没采用："信息更多"没有稳定定义，按输入顺序才可复现；被并入的名字保留在别名里，不丢信息。

- **后来的条目同时连到两组时把两组合成一组（桥接合并）。** 最强理由：模型把同一人拆成三条、第三条恰好同时带着前两条的名字时也能一次合并干净。没采用：最常见的桥接条目是用通用称呼命名的路人（"男子"），它会通过两人共有的别名把两个不同的人并成一个，名字被降为别名、描述被路人的覆盖、两人之间的关系被当作自环删掉；这比少合并一次的代价大得多，也违背了"只共享别名不合并"的保证。
- **共享别名照旧合并，另设一张通用称呼停用词表（男子、老板、警察、单字等）。** 最强理由：两条真名不同、靠一个具体别名相连的条目仍能合并。没采用：停用词表永远列不全，模型换个说法（"中年男人""那个人"）就漏过；"至少一边是名字"是结构性的条件，不依赖词表。

## Consequences

- 收益：索引里的剧情时间都是合法的 `MM:SS` 且在片长内；同一人只剩一条，关系不再分裂，brief 的 Characters / Relationships 段不再重复。旧 work_dir 的索引在下次理解或下次生成 brief 时免费修好。
- 代价：只共享别名的两条不再合并，模型若把同一人写成两个不同名字、只靠一个共同别名相连，这两条会保留为两人；模型把某人的名字写成另一人的别名时仍会误合并。一条条目若同时带着两个不同角色的名字（真是同一人被拆成三条），也只会单独保留，三条都留在索引里，等写稿 Agent 自己判断；链式拆分（甲—乙相连、乙—丙相连、甲丙不相连）同样让乙成为桥，三条都不合并。同名条目一律视为同一人，模型给两个不同的路人起同一个名字时会被并成一条。判断桥要比较每对相邻节点，是角色数的三次方，索引里的角色只有几十条，可以忽略。被删掉 `time` 的剧情节点只剩顺序。合并只看名字与别名，不看描述。
