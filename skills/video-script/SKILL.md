## 1. 定位

如果任务只改宣发标题、封面字、花字或回填外部文案，直接读 `references/promotional-copy.md`，按当前短片的看点和片内兑现位置修改指定文字层，不必重跑下面的策划与旁白流程；普通解说写稿也不额外增加平台调研或包装步骤。

本技能负责确立创作方向、规划声画分工、撰写旁白并完成校验。Agent 依次从五个视角做决定：

1. 导演
2. 故事编辑
3. 画面剪辑师
4. 声音/旁白编辑
5. 第一次观看的观众

先落盘简洁的创作决定，再写时间线文件。`validate.py` 只对照理解索引做机械校验，绝不改写 Agent 的文稿：段落顺序、数量、时间戳、正文、停顿和扩展字段原样保留，仅根据实测声音证据回写 `overlaps_speech`。时间窗装不下文本或段落时间倒序等问题，一律报 error 退回给 Agent 修改。

下文中的 `scripts/...` 均相对于本技能目录；若从仓库根目录调用，请补上本技能的绝对路径。

### 1.1 创作控制模式

动手前先根据用户要求和 `work_dir` 现有文件判断本轮创作控制模式（与 `full|cut|dub` 渲染模式相互独立）：

- **CREATE**：首次创作。先比较至少两个立得住的故事与剪辑方案，再择优落盘。
- **DIRECTED**：用户已指定结构、镜头、台词或语气。直接照准落实，不要为了走流程硬凑备选方案。
- **REVISION**：用户看片后提修改意见。以最新反馈为准，未点名的部分默认锁定不动。

REVISION 模式下先列清“本轮修改项”和“锁死项”，再定点改对应文件：口播腔调、节奏或字幕断行意见写进 `style_card.json`；选镜、出入点、表演细节和声音主导权写进 `visual_audio_board.json`；只有核心看点、叙事视角（POV）、故事主线或戏剧节拍（beat）变动时，才更新 `recap_story_plan.json`。已删掉的镜头、原声或句子要同步从计划文件里清理干净，别留失效锚点，更不要把局部返修重做成一轮全盘推翻的 CREATE。

## 2. 远程调用与数据外发

本技能只有 `review.py`（§7.1 的建议型语义评审）会联网。其余步骤全部在本地完成：`validate.py` 及其格式与文风检查只读写 `work_dir` 内的本地文件，不发起任何网络请求；策划与写稿也由 Agent 直接读写 `work_dir` 完成。

`review.py` 发送目的地：

- 发往 MiMo 的 OpenAI 兼容接口 `<MIMO_API_URL>/chat/completions`，使用 `MIMO_API_KEY` 认证，默认模型为 `MIMO_MODEL`（默认 `mimo-v2.5`）。未设置 `MIMO_API_URL` 时，按量计费 key 发往 `https://api.xiaomimimo.com/v1`，`tp-` 开头的 Token Plan key 发往 `MIMO_TOKEN_PLAN_CLUSTER` 指定的集群（默认 `https://token-plan-cn.xiaomimimo.com/v1`）。
- 未设置 `MIMO_API_KEY` 时脚本立即退出，不构造也不发送任何请求。

`review.py` 外发内容（仅发文字，不上传视频、抽帧图片或音频文件）：

- `narration.json` 中全部旁白段的时间戳与正文。
- 理解索引的文字摘录：从片头、中段、片尾、长留白及各段旁白附近抽出的时间窗内，提取 `vlm_analysis.json` 的场景描述与 `frame_facts`，外加对应对白转写（优先读 `asr_clean.json`，无则读 `asr_result.json`）。
- `background_research.json` 中的剧情梗概、角色简介、人物关系与故事线摘录。
- 若存在 `packaging_plan.json`、`recap_story_plan.json`、`visual_audio_board.json`、`style_card.json`，各截取前 3000 字一并附上，同时附带 `original_subtitles.json` 的原声字幕文本。
- 素材较长时自动分块请求；评审结果仅写回本地 `narration_review.json` 与 `narration_review.md`。

运行条件与关闭方式：

- 单独调用本技能时，`review.py` 只在用户或 Agent 主动执行该命令时运行；不执行就零外发。若用户不希望文稿离开本机，跳过 `review.py`，人工复核后直接运行 `validate.py`。
- 端到端编排默认在合成配音前调用一次 `review.py`，评审失败也不阻断主流程；可通过编排参数 `--no-review-narration` 或环境变量 `REVIEW_NARRATION=0` 关闭。若显式开启了严格评审（`--require-narration-review` 或 `REQUIRE_NARRATION_REVIEW=1`），则必须执行评审，关闭开关不再生效。
- 评审只出报告、绝不改动 `narration.json`，采纳与否由 Agent 或用户拍板。

## 3. 读取素材并确认状态

动笔前依次查看 `work_dir` 中的素材：

- `agent_narration_brief.md`：场景切分、时长、安静窗口与各窗字数上限。
- `asr_writing_chunks.json`：按语义切好的原声长对白分块。
- `timeline_fusion.json`：快速核对某段时间里是对白密集区还是可开口的静音槽。
- `vlm_analysis.json` 与 `asr_result.json`：核查具体动作与原话；若有 `asr_clean.json`，一律以清洗后的台词为准（校验、评审、剪辑和合成均读该文件）。
- 简报顶部列出的抽帧故事板（storyboard）：别只看文字摘要，人物变脸、顿住、眼神躲闪和台词前后的微表情往往才是真正值得落笔的瞬间。
- `production_reference.json`（存在时读取）：从参考成片拆出的叙事结构与节奏测量值，具体取舍见 §4。

`full` 模式全程使用原片时间戳。`cut` 模式分两步走：第一阶段只按原片时间写 `clip_plan.json`；等剪出 `edited_source.mp4` 后，第二阶段再按剪后成片时间（OUTPUT 时钟）写 `narration.json`。

落盘任何文件前，先看 `work_dir` 里的现场状态：

- 读 `recap_run_manifest.json` 确认 `edit_mode`、源视频列表和本轮配置。
- `full` 模式：还没有 `narration.json` 就直接写稿；已有旧稿则先对照画面和反馈复核，再跑校验。
- `cut` 第一阶段：目录里还没有 `clip_plan_validated.json` 和 `edited_source.mp4`，此时只写 `clip_plan.json`。
- `cut` 第二阶段：上述两个文件已就位，先对照 `clip_plan_validated.json.clips[]` 里的 `source_start/end` 与 `output_start/end` 核准时间映射，再写基于成片输出时间的旁白。

下笔时务必确认旁白没有横跨剪辑硬切点，也没有引用已经被剪掉的画面或台词。

## 4. 制定创作方案

先读 `references/creative-editing-playbook.md`，再按当前创作控制模式新建或更新以下文件：

1. **`recap_story_plan.json`**：写明导演意图、CREATE 模式下的至少两个候选结构假设、最终选定的主视角（POV）与主线，以及每一拍（beat）带来的实质变化。DIRECTED 与 REVISION 模式直接写选定方案，不硬凑假备选。
2. **`visual_audio_board.json`**：逐拍落实画面任务、要保住的表演或反应瞬间、入点与出点理由、声音主导方（`audio_owner`）、原声锚点及旁白任务（`narration_job`）。
3. **`style_card.json`（按需）**：记录当前认可的讲述人设、口播节奏、字幕断行习惯与用词禁忌。收到文风或字幕反馈时先更新这张卡，再改旁白稿。

所有计划文件只写拍板结论、证据锚点、淘汰原因和简短理由，不要贴大段思考过程。

如果 `work_dir` 下有 `production_reference.json`，先读再定方案。它只是从另一部成片提炼出的结构与节奏参考，不包含本片事实，绝不能拿来当本片的画面或台词依据。优先级固定为：**用户指令 > 本片画面与原声证据 > 参考片数据**。CREATE 模式可以把参考片的 `structure` 当作候选假设之一，跟根据本片素材长出来的方案同台比较；DIRECTED / REVISION 模式默认不套用。参考片里的 `targets` 只是参考区间而非硬指标，一旦与本片必须保留的台词或反应镜头冲突，无条件服从本片素材。需要记录取舍时，可在 `recap_story_plan.json` 中加可选字段 `reference_methods: [{"id": "m1", "decision": "adopt|adapt|skip", "note": "…"}]`。

### 4.1 导演判断

动笔前先拍板六件事：

- **观众承诺**：点进来的人看完这一条，到底能看爽什么、揪心什么或搞懂什么？
- **主视角（POV）**：全程跟着谁的处境和眼睛走？
- **核心悬念**：勾着观众一直划不走的那根刺是什么？
- **情绪起落**：开场是什么气压，结尾落在哪口气上？
- **藏与露**：哪张底牌先压住不说，留到哪一拍掀开才最炸？
- **结尾余味**：最后一幕定格时，留给观众的是唏嘘、爽快还是后背发凉？

### 4.2 故事编辑

CREATE 模式先拿两个立得住的叙事方案比高下，再选更能打动人的一条；DIRECTED / REVISION 直接沿用既定主线。每一拍（beat）都必须让局势发生肉眼可见的推进——要么知情范围变了，要么强弱易位、目标改向、关系撕裂、情绪反转或代价升级。如果把某一拍抽掉，前因后果、人物立面和情绪劲头丝毫不减，这一拍就该果断砍掉。

### 4.3 画面剪辑

选镜头是选“最扎人的那一秒”，而不是按流水账搬运事件。逐拍权衡：

- 看说话的人，还是看听话那个人脸上骤变的表情？
- 看动手的过程，还是看挨了一下之后的反应？
- 能不能晚半秒进，直接切在冲突已经在脸上的瞬间？
- 能不能早半秒出，或者在关键眼神上多停半秒让劲儿透出来？

在不剪碎前因后果的前提下尽量晚进早出，但那口气、那个迟疑、那记耳光清脆的声响和刺痛人心的完整原话，一帧都别误砍。

### 4.4 声音与旁白分工

每一拍先定“谁当家”（`audio_owner`），再决定旁白开不开口。旁白的 `narration_job` 只能取以下六种之一：

- `context`：补齐画面看不见但懂戏必须知道的前情或关系；
- `causal_link`：把剪辑跳过的因果链条扣死；
- `foreshadow`：埋下一颗后文马上会炸响的钉子；
- `interpretation`：根据画面细节，点破人物嘴硬背后的代价或算计；
- `transition`：交代时间跨越、场地切换或视角流转；
- `none`：画面、原声对白、动作声或沉默自己就能把戏演足，旁白闭嘴让位。

只要原片的一句狠话、一声冷笑或两秒死寂比解说更有劲，就果断标 `none`，别用旁白把好戏糊住。

### 4.5 cut 模式第一阶段

`cut` 模式第一步只根据 `recap_story_plan.json` 和 `visual_audio_board.json` 写出基于原片时间的 `clip_plan.json`，这一步先不写 `narration.json`：

```json
{
  "target_duration": "10m",
  "clips": [
    {
      "start": 12.0,
      "end": 38.0,
      "reason": "b01 | hook | knowledge: unknown→threat | POV=沈曼 | 撞见未婚夫搂着千金谈联姻 | 入点=推门看清两人动作 | 出点=转身攥紧户口本"
    }
  ]
}
```

`reason` 字段固定用竖线分成 7 段：

```text
beat_id | function | change | POV | preferred moment | 入点 | 出点
```

选出的片段排在一起必须能顺畅讲完一件事，不能拼成毫无因果的“名场面集锦”。开头最多放 1 个抓人的冷开场（cold open），随后老老实实按“立处境（setup）→ 变故突起（turn）→ 步步紧逼（escalation）→ 亮底兑现（payoff）”往下推。每段长短由戏眼决定，别拿固定秒数硬切；片尾最后一刀必须保住完整的台词落音或动作收势。遇到高频切镜区间时，按剪辑阶段的规则区分原片快切与拼接碎切，绝不人为剪出闪烁感。

## 5. 撰写旁白

`full` 模式直接按原片时间写；`cut` 第二阶段先看剪好的 `edited_source.mp4` 和剪后故事板，在 `visual_audio_board.json` 里补齐输出时间并重核一遍 `audio_owner` 与 `narration_job`，再按成片输出时间落笔：

```json
[
  {
    "start": 5.0,
    "end": 12.0,
    "narration": "相恋五年，她揣着户口本去求婚，推门却撞见未婚夫正搂着叶家千金谈联姻。",
    "pause_after_ms": 250,
    "overlaps_speech": true,
    "emotion": "冷静克制"
  }
]
```

字段说明：

| 字段 | 含义 |
|------|------|
| `start` / `end` | `full` 模式填原片秒数；`cut` 第二阶段填成片输出秒数。与上一块间隔不超过 1.6 秒的相邻块视为同一口播段落，合成阶段会让后一块紧接前一块实际语音结尾（留 0.35 秒气口）播出，最多比 `start` 提前 1.2 秒，且提前部分绝不踩进原声对白；段落首块严格从 `start` 起播，前一块若超时则自动顺延 |
| `narration` | 旁白正文 |
| `pause_after_ms` | 块尾停顿毫秒数，默认 250ms |
| `overlaps_speech` | 是否允许压在原声对白上；压低原声持续解说的窗口填 `true`，纯静音空档填 `false` |
| `emotion` | 传给 TTS 的整块情绪/语气标签 |

### 5.1 写作规则（解说质感与去 AI 味）

1. **先领任务再开口**：每一块旁白都必须对应明确的 `narration_job`；没活干的地方把时间留给原声和画面。
2. **具象处境 + 反差直给，3 秒立住钩子**：开场不要铺垫世界观、时代背景或抽象情绪，直接甩出“具体场合 + 手头动作/物件 + 身份或利益反差”。
   - 差例（AI 摘要腔）：`这是一段关于隐忍与背叛的故事，面对未婚夫的变心，她做出了惊人的决定。`
   - 好例（具象解说感）：`相恋五年，爷爷病危想看她结婚，苏曼揣着户口本去找秦斯礼，却在门外听见他搂着叶家千金嗤笑自己只是个养熟的情人；她当场收起户口本，转头就跟他的死对头领了证。`
3. **用肉眼可见的动作和当场后果，换掉书面报告词**：严禁使用“完成认知闭环”“内心防线崩塌”“关系发生位移”“情绪锚点”“命运的齿轮”等公文味、AI 味词组。人物有多狠、多痛、多心虚，全靠手头动作和即时反应写出来。
   - 差例（报告总结腔）：`面对母亲的偏心与冷漠，她的内心彻底绝望，双方的亲情关系降到了冰点。`
   - 好例（动作咬合结果）：`她捂着刚拆线的刀口递上出院小结，亲妈看都没看，一把揉成废纸扔进垃圾桶，转手就把抹布和水桶塞进她怀里，催着她给弟弟擦地办生日宴。`
4. **原声台词前后的「垫半句、让半句、接半句」**：好解说从不跟原片抢台词，而是帮原声“蓄力”。原声开口前，旁白只垫半句“他不知道门外是谁 / 她还在等一句解释”；原声说出那句最扎心的话时，旁白彻底闭嘴让出声道；原声落音后，下一块旁白立刻接上人物骤变的脸色或反手动作，绝不把原声刚说的话复述一遍。
5. **一口气顺下来的口播长短句**：同一拍里的旁白按“所处境地 → 突发动作 → 当场后果/言外之意”一气呵成，交给一次 TTS 连贯读完。句号跟着真人口播的换气走，别为了迁就字幕宽度把一句话剁成三四个碎块，更不要一句一停。
6. **7:3 只是防满铺的粗略参考，不是硬配额**：只有在缺乏更细声画判断时，才拿七成解说、三成原声当底线防呆；一旦遇到高能对峙、巴掌落声或窒息沉默，整拍都可以全交给原声。
7. **扣准有效语速与首尾气口**：按 `字数 / 简报顶部 speech budget` 估算实读秒数，每块还要额外留出约 0.45 秒的 TTS 首尾静音。简报里每个窗口提示的字数尚未扣除这 0.45 秒，遇到 2–3 秒的窄窗口要主动少写一两个字；塞不下就砍掉枝蔓或拆拍，别靠硬塞字数逼合成器倍速赶稿。
8. **画面之外有增量，句句落回证据**：观众一眼就能看懂的“他站起来、她走过去”绝不啰嗦；旁白只补前因、关系、暗藏的算计或时间跨越。所有人名、动机和潜台词都必须能对应到画面、台词、调研资料或用户说明，不能把背景资料里的前史硬说成当前镜头正在发生的动作。
9. **少用假转折，彻底禁用破折号**：口播稿一律不用破折号（`——`），也不写半截话。少用“不是 A，而是 B”这种先立假靶子再纠偏的套路句——除非观众顺着画面真会误判，否则直接写人物干了什么、换来什么后果。

### 5.2 解说结构

- **钩子（Hook）**：前两句直接亮出人物卡在什么绝境、手里攥着什么筹码，抛出的悬念必须在正片里真刀真枪兑现，不搞标题党空头支票。
- **主线（Spine）**：死死咬住选定的主视角（POV）和核心矛盾往前推，别每切一个场景就重新起头介绍一遍。
- **递进（Escalation）**：每一拍都要比上一拍更逼人——要么筹码加码，要么遮羞布被撕开，要么退路被堵死。
- **留扣（Planted Gap）**：只在后文真会翻底牌的地方埋钩子，不留没下文的烂尾悬念。
- **收束（Payoff）**：结尾正面接住或反转开头的困局，定格在最有后劲的动作、眼神或一句话上。
- **声画咬合（Handoff）**：旁白与前后的原声台词同属一拍——旁白架起火候，原声亮出刀子，下一句旁白接住出血的后果。

### 5.3 原声留白字幕

需要在留白段打出原声台词时，可按成片输出时间编写 `original_subtitles.json`：

```json
[{"start": 15.0, "end": 17.0, "text": "原声台词"}]
```

只收录留白区里真能让观众听清的关键原话，顺手订正 ASR 同音错字与角色名，单条尽量压在一行以内；被旁白压住或已剪掉的对白一律别写。不写该文件时，合成阶段会用保守的 ASR 映射自动兜底。原声字幕只在底部遮罩盖住了原片字幕、或用户明确要求重打原声字幕时渲染，并自动加上 `「」` 与解说词区分。

## 6. 创作自审

跑语义评审脚本前，先把自己当成第一次点进来的观众，抽掉其中一层做对照自检：

1. **抽掉某一拍**：如果拿掉这一拍，前因后果、人物劲头和结局冲击力一点没少，说明是注水拍，直接删。
2. **对调说话人与听话人镜头**：台词响起时，看对面那个人瞳孔收缩或攥紧拳头，是不是比看说话人动嘴皮子更有戏？谁更有戏就留谁。
3. **关掉旁白光看画面和原声**：人物在争什么、谁占上风、情绪在哪一秒绷断，光靠画面和原声能不能立住？
4. **闭上眼光听声音**：把旁白和原声连起来听，像不像一个会讲故事的人在耳边复盘，还是像断断续续的盲人摸象字幕？
5. **把某句旁白换成原声或两秒沉默**：如果闭嘴让角色自己把话说完更有力量，立刻把这一拍的主导权还给原声。
6. **首尾对表**：开头吊起胃口的那个问题，结尾到底给没给痛快话？
7. **顺读断句**：把相邻短句连起来大声读一遍，能一口气顺下来的就合进同一个解说块，绝不因为字幕要换行就把 TTS 朗读稿切碎。

每次自审只抓最影响观感的 1–3 个硬伤动手改：先调结构与选镜，最后再抠字眼。

REVISION 模式还必须逐条勾对：用户点名要改的地方是否已彻底改到位、未点名的锁定区是否纹丝未动、`style_card.json` 与 `visual_audio_board.json` 里是否还残留已废弃的镜头或旧词。除非用户主动要多版对比，否则不要擅自发散新方向。

## 7. 评审与校验

### 7.1 建议型语义评审

```bash
python3 scripts/review.py --work-dir <work_dir>   # 会联网：外发内容与关闭方式见 §2
```

脚本会自动识别 `cut` 模式，只要目录里有已校验的剪辑计划和剪后成片，就自动按输出时间线核对；加 `--timeline source` 可强制按原片时间核对。跑完打开 `narration_review.md`，优先消灭 `error` 级别问题（尤其是 `category=hallucination` 的无据脑补）。

修改后重跑评审，直到满足以下任一条件：

- `verdict` 为 `PASS` 且零 `error`；
- 对决定保留的争议项写下明确的覆盖说明（override）。

覆盖说明追加写入 `work_dir/narration_review_override.md`：

```markdown
### 覆盖记录 — <date>
- 问题：segment 4 / category=hallucination
- 评审意见：“他早已知情”缺少画面/对白依据
- 决定：KEEP — 该事实来自用户提供的当前集背景，而非未来剧情
- 签署：<agent/human>
```

`review.py` 只生成报告，默认作为参考建议、出错时不阻断主流程；若调用方显式开启严格评审，事实冲突、残句、解析失败或接口不可用都会在进入 TTS 前直接拦截。覆盖记录仅供人工审计留档，`review.py` 与 `validate.py` 不会读取它。

### 7.2 确定性硬校验

```bash
python3 scripts/validate.py --work-dir <work_dir> --mode full
# cut 输出时间线由编排器使用 --mode cut_output
```

该命令写出 `narration_lint.json`。`full` 与 `cut_output` 模式共用同一套声音归属算法（用原声对白区间扣掉安静窗口）回写 `overlaps_speech`，其余字段一字不改，不截断、不合并、不补标点、也不重排顺序。推荐字数按窗口时长先扣掉 0.45 秒 TTS 首尾静音再折算；`full` 模式下单段字数一旦超过推荐值的 1.25 倍，立即报 `over_budget` error，并在报告里列明时间窗、`budget_chars`、`limit_chars`、`actual_chars` 和 `over_chars`。遇到超字数请直接精简文稿或挪宽时间窗，别指望靠 TTS 加速硬塞。一旦存在 error，脚本以非零状态码退出，按人类可读的「段 N」（对应 `narration.json` 第 N 块，从 1 起算；`narration_lint.json` 内的 `index` 仍从 0 起算）逐条列出错误码、关键数值与修改方向。修完所有 error 后重跑，直到校验全绿再进配音与合成。

若片名或题材已知但缺少人物与前情背景，动笔前先按 `references/research-guide.md` 补写 `background_research.json`。遇到画面与对白信息量都很薄的素材时，简报里的建议段数只能当上限：宁可少写几段、句句扎实，也别为了凑够段数去干巴巴地复述画面。

## 8. 能力边界

- 本技能不跑 ASR / VLM 识别，不调 TTS 合成语音，也不渲染视频，只消费视频理解阶段产出的索引文件。
- 唯一会发起网络请求的是 `review.py` 的 MiMo 文字评审（见 §2）；`validate.py` 与本地文风检查全程离线运行。
- 平台热梗与竞品调研仅在用户明确交代宣发任务时启用，绝不拿外部爆款套路替代本片事实，也不默认改动正片剪辑与解说主线。
