# 创作剪辑工作法

本参考只规定 Agent 的创作判断，不增加渲染模块。进入剪辑或写稿前，先完成这里的决策，再写 `clip_plan.json` 或 `narration.json`。

## 先判断创作控制模式

- **CREATE**：没有既定成片方向，可以比较故事/剪辑假设并选择。
- **DIRECTED**：用户已经指定结构、镜头、台词或表达，目标是准确落实而不是展示替代创意。
- **REVISION**：基于已有版本看片修改。最新反馈覆盖旧决定；本轮未点名内容默认冻结。

REVISION 先列本轮修改项与冻结项。表达、节奏、字幕意见写回 `style_card.json`，镜头与声音意见写回 `visual_audio_board.json`；只有故事主线改变才更新 `recap_story_plan.json`。删除内容时也删除过期的计划描述。只提能定位到 beat、镜头边界或句子的具体局部修法，未点名层继续冻结；完成后分别验证“该变的确实变了”和“不该变的没有漂移”。

## 决策优先级

硬约束先于审美：

1. **证据真实**：人物、关系、因果和结果必须由画面、对白、可靠背景或用户上下文支撑。
2. **声音可懂**：关键原声不能被截成半句，旁白不能把必须听见的对白完全盖住。

硬约束满足后，发生冲突时按以下顺序取舍：

1. 情绪与人物；
2. 故事推进；
3. 节奏；
4. 视线与画面连续；
5. 技术上的“绝对工整”。

不要为了连续而牺牲人物反应，也不要为了快而删掉真正改变观众感受的瞬间。

## 五次专业判断

### 1. 导演：先决定观众经历什么

先回答，而不是先写开场文案：

- 观众承诺：看完具体会理解、担心或感受到什么？
- POV：这条内容主要跟随谁的经历？谁不是主视角？
- 戏剧问题：观众一直想知道的那个问题是什么？
- 情绪路径：开头的情绪如何变成结尾的情绪？
- 隐瞒与揭示：什么信息暂时不说，何时揭示才最有力量？
- 结尾余味：答案落地后，观众最后应留下什么感受？

CREATE 至少提出两个可成立的剪辑假设，再选一个。比较的是叙事效果，不是措辞：例如“按主角认知逐步揭示”与“先展示后果再追问原因”。DIRECTED / REVISION 沿用用户指定或已确认的主线，不为满足模板重新发散。只记录当前选择与理由，不输出冗长思维过程。

### 2. 故事编辑：把素材组织成变化

beat 不是固定秒数、场景名或一句旁白；beat 是一次可感知的变化。每个保留 beat 至少改变一项：

- 观众知道了什么；
- 人物想要什么；
- 谁占上风；
- 关系如何移动；
- 情绪如何转向；
- 风险或代价如何升级。

如果移除一个 beat 后，因果、人物或情绪都没有损失，它通常不值得占用成片时间。精简不能只保“发生了什么”：还要保住人物动机、接受条件，以及人物为何犹豫或行动；缺前提时回到源证据，用更短的原声或解说补齐，不恢复无关长铺垫。钩子必须提出这条故事真正会兑现的问题，不能制造正文不回答的夸张承诺。

准备移交剪辑时，把这类不可删除的具体源时刻写入同一 `clip_plan.json.required_evidence`：`nodes` 每项记录唯一 `id`、实际文件绝对路径 `source`、原片秒 `start/end`、`track`（audio/video）和 `content`；多源可补 `source_id`。`before` 用 `[前提id, 回应id]` 登记本片必需的顺序。只锁必要区间，不锁整个 beat；不依赖 `reason` 里的“保留前提”一句话。剪辑执行器会在吸附剪点后核对这些要求，缺段时先修选择，再配音包装。

### 3. 画面剪辑：选择时刻，而不只选择事件

对每个 beat 做以下判断：

- **入点**：能否晚一点进入，跳过已经能推断的铺垫？
- **出点**：信息或情绪落地后，能否早一点离开？
- **表演**：说话者与倾听者谁更能承载此刻？动作与反应谁更重要？
- **不可替代瞬间**：停顿、迟疑、失误、眼神、动作声音中，哪一个让人物变得真实？
- **节奏**：这一拍需要冲过去，还是需要多停半秒让含义落地？
- **边界**：优先完整动作、完整台词和自然声音边界；不要机械地把每个片段切成同一长度。
- **兑现**：以某个可见结果为看点时，只写证据已呈现的结果，不推断更强的结果（例：证据只到受击，就不能写成倒地或胜负）。

进入 `clip_plan.json` 的不是“发生过的所有重要事件”，而是最能让观众经历这条主线的具体时刻。

目标不是绝对最短，而是**最短但完整**：晚进不能丢掉理解动作所需的前提，早出不能吃掉表演的回报。建立空间和事实的镜头通常可以短；关键对视、亲吻、受伤反应、决定落地或沉默可以多停一点，让观众先感受到再离开。有情感回应或知情变化的反应镜不是冗余，不能仅因它是反打或停留较短就机械删除。

场景之间的 IN / OUT 也要有任务：

- 新人物、地点或情绪场景，先给画面一个可感知的建立时刻，再让旁白进入；旁白不必与画面同帧起跑。
- OUT 优先落在动作完成、反应落地、台词句末、沉默结束或干净硬切前。
- 不要在原片叠化、闪白或其他转场的中间再切一次。转场至少由画面变化、动作延续、声音接力或叙事跨越中的一项驱动。
- 跨场镜头只能作明确的并置或主题呼应，不得拼成同场出手、接触、反应的虚假因果；花字只能补有证据的必要前提，不能替补源证据或提前宣布结果。

scene-change score、逐帧亮度和接点 contact sheet 只用于诊断：检查每个接点前后约 0.5–1 秒，定位硬切、白闪或曝光叠化候选。修复优先收进稳定镜头、保留原片完整转场的一侧、扩展源素材，或用相邻有效镜头补足时长；不能为了视觉干净切断台词。最终必须真实播放接点，不能把检测分数当成观看结论。

对短时间频繁切镜头的段落，先用 ffmpeg scene filter 输出候选时间，例如：

```bash
ffmpeg -i input.mp4 -vf "select='gt(scene,0.35)',showinfo" -an -f null -
```

阈值只用于召回候选，闪白、叠化和大幅运动都可能误报。把候选映射回 source 区间和成片拼接边界后再分类处理：

- **原片切点**：无关的短镜头按完整 source shot 删除；相关但停留过短、看起来像闪一下的镜头，向前/后扩展到完整动作、反应、台词或下一个干净切点。这里的“拉长”是多保留真实源素材，不默认用定格或慢放制造不存在的表演。
- **本次剪辑制造的切点**：优先移动 IN / OUT、恢复同一源镜头的连续运动、合并相邻片段，或换成有叙事任务的连接镜头；能消除就不保留。溶解、闪白和包装不能用来遮掩坏接点。
- **有意的原片蒙太奇**：只有当每个短镜头都提供新信息、动作或节奏回报，且正常播放仍清楚可读时才保留；否则按无关或过短镜头处理。

密集度不是单一固定秒数门槛。反打是否保留取决于它有没有新增信息，例如关系、情感回应、知情变化或空间/动作结果，而不是是否达到统一时长；先找同一短窗内的连续候选，再以正常速度播放判断观众感受到的是有效节奏还是闪烁。

### 4. 声音与旁白：先分工，再写字

每个 beat 先指定一个主要 `audio_owner`：

- `original_dialogue`：原对白本身就是事件或表演；
- `action_sound`：动作声音承担冲击、因果或空间感；
- `ambience` / `music`：环境或音乐承担情绪；
- `silence`：沉默、停顿或呼吸是内容；
- `narration`：画面和原声无法独自交代必要的上下文、因果或预期。

只有当旁白有明确工作时才写。`narration_job` 只能从以下任务中选择：

- `context`：补充看不见但必要的背景；
- `causal_link`：连接被压缩掉的因果；
- `foreshadow`：建立稍后会兑现的预期；
- `interpretation`：基于证据指出人物选择、关系或代价；
- `transition`：跨越时间、地点或素材来源；
- `none`：画面、原声或沉默已经足够。

`7:3` 只可作为没有更好判断时的粗略首稿参考，不是质量目标或覆盖配额。强对白可以让一个 beat 完全没有旁白；信息密集的压缩段也可以由旁白主导。

旁白拥有一个 beat 时，先写成一个连续思路，常见推进是“前提 → 触发动作 → 变化/意义”。句子数量不是目标；一个完整长句或少量相连句都可以，关键是一次 TTS 能自然说完而不是一句一停。字幕可以为阅读拆成多个 cue，但不能反过来把朗读稿切成碎 utterance。

“不是 A，而是 B”只在素材确实需要纠正一个可能的旧判断时有价值。不要先虚构错误判断，再用肯定句制造洞察；能直接写动作、因果和后果时就直接写。

### 5. 观众复核：从第一次观看出发

完成草案后做三次反事实检查：

1. **静音旁白**：只看画面和原声，人物、变化和关键情绪是否仍可感知？
2. **只听声音**：旁白是否形成一条可听懂的主线，而不是字幕腔或画面复述？
3. **第一次观看**：开头承诺了什么、每一拍又打开了什么问题、结尾是否真正回答？

再逐 beat 追问：

- 删除它，什么会坏？什么都不坏就删。
- 删除或换掉反应镜头后，是否丢失情感回应、知情变化或新的动作结果？
- 旁白改成原声或沉默，含义是否更好？
- 提前揭示或延后揭示，哪一个更符合 POV？
- 能否晚进、早出，而不损失理解？

只优先处理 1–3 个最高回报修改，避免用大量低价值润色掩盖结构问题。

准备交付时，把抽象的“第一次观看”落实成动作：正常速度完整播放实际最终文件；逐个播放接点前后；完整只听声音；再单独复看开头、核心情绪点和结尾。脚本、样帧与自动 QC 只能辅助定位，不能替代完整观看。

这些是简洁的决策记录，不是公开的完整思维过程。CLI 可以忽略它们，但后续 Agent 与建议型评审会使用它们保持创作一致。

```json
{
  "schema_version": 1,
  "items": [
    {
      "beat_id": "b01",
      "source_id": "可选，多视频时填写",
      "source_start": 12.0,
      "source_end": 20.0,
      "output_start": null,
      "output_end": null,
      "picture_job": "orientation|evidence|performance|reaction|action|contrast",
      "preferred_moment": "具体要保留的画面时刻",
      "entry_reason": "为什么从这里进入",
      "exit_reason": "为什么在这里离开",

```

cut 第一阶段先用原片时间写；`edited_source.mp4` 产生后，在第二阶段补上输出时间并重新确认 `audio_owner` / `narration_job`。

## 内容质量基线

进入 TTS 前，以下问题都必须能用具体 beat 回答；否则先改计划或脚本：

1. **承诺**：开头提出的真实问题，结尾是否兑现？
2. **主线**：是否有一个明确 POV 和一条主导因果/关系线？
3. **变化**：每个 beat 是否改变知识、权力、目标、关系、情绪或风险？
4. **人物**：是否保留了至少一个不能由剧情概述替代的表演/反应瞬间？
5. **视听分工**：每个 beat 是否明确由画面、原声、沉默或旁白中的谁主导？
6. **必要性**：旁白是否都在增加信息或期待，而不是复述像素？
7. **完整观看**：实际最终文件是否完整看过、逐接点看过并只听声音检查过？

这套基线与抖音、YouTube 或任何平台数据无关。先让内容本身成立，再讨论标题、封面、时长档位和发布优化。
