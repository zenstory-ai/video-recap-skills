# 生产能力边界与验收原则

通用技能库只负责提取素材证据、承接创作决定、执行配音与渲染成片；针对单个剧集或客户的定制配置与交付管理，一律留在调用方自己的项目目录中维护。各技能的具体功能与命令行参数见对应的 `SKILL.md`。

## 通用核心、按需适配与单项目数据的分工

| 层级 | 职责边界与处理方式 |
|---|---|
| **剪辑/解说通用核心** | 素材证据提取、故事与选镜决定、完整语音合成、原声与 BGM 混音分工、字幕时序对齐、按既定风格渲染及真实成片质检。这部分统一收敛在自包含生产技能 `video-recap` 内；按需调用的 `video-reference` 仅负责把已有成片拆解为制作参考，不介入日常生产流水线。 |
| **按需启用能力** | 自托管 TTS 端点与音色、主画窗区域（ROI）切点检测、静态包装图层叠加、剪映草稿导出。仅在用户显式传参时启用，绝不为普通剪辑任务增加额外的必填配置。 |
| **项目或操作者事务** | 交付批次台账、成片体积上限压制、多平台分发上传、共享网盘同步、临时磁盘清理。这类事务不进核心技能库，也不内置任何后台常驻进程或自动删文件逻辑。 |
| **单项目私有数据** | 批次编号、集数清单、特定剧集的裁切画窗/帧率、专有字体与台标、片尾固定时长、特定声线 ID 与混音增益数值。一律存放在调用方自己的项目配置或计划 JSON 中，不写死为通用默认值，也不混入公共文档示例或测试金标。 |

一条硬检验标准：**如果某个数值、路径或特殊处理只对某一部剧成立，它就不该写进这个仓库的核心代码。** 文档里的示例应使用一眼就能看出是演示用的合成参数（如非标准画幅、合成音频），单元测试夹具则从各自独立的常量推导，绝不硬编码任何真实商业交付项目的帧号、数据包计数或回归编号。

## 三层验收各司其职，严禁互相冒充

- **机械确定性事实**：时间戳范围、文件大小与修改时间、帧数、解码完整性、成片真峰值响度等，完全由脚本做确定性校验，不合规则直接阻断。
- **辅助定位证据**：粗窗语音转写（ASR）、切点分数（scene score）候选、抽帧拼图、剧情证据链。它们只能帮人快速缩小排查范围，自身存在精度上限与漏报盲区；产物中必须如实标注精度等级（粗粒度分窗 / 比例估算 / 能量校准）与未检查项（`NOT_CHECKED`）。
- **活人创作与看感判断**：开头抓不抓人、演员反应留得够不够、配乐贴不贴脸、最终成片原速播放顺不顺耳。**JSON 结构合法或自动化测试全绿，绝不等于成片好看好听。**

## 把交付纪律变成脚本能拦住的硬门禁

如果交付红线只写在给 Agent 看的提示词里，一旦多轮返修就极易被绕过。本仓库的做法是把客观可测的底线直接写成执行器的阻断逻辑与可对账回执：

- **默认绝不擅改文稿**：解说词一旦塞不下时间窗（在允许的有界提速内仍装不下），合成前直接以 `no_safe_fit` 报错退回改词或扩窗，绝不允许 TTS 擅自删字或靠裁切尾音硬塞。
- **声音模式显式隔离**：标准解说（`narration`）与原声配乐混音（`--audio-mode source-mix`）两条路径严格分流，切换模式必须换用新工作目录，防止旧产物串味。
- **落盘音频全链路可对账**：`_placed_*.wav` 由本轮输入重建并与序列化后的 `timeline.json` 严格对账；只改外层画面或包装时仍会走混音与 AAC 重编码（若需零重编码逐包拷贝既有 AAC 音轨，请固定使用 `v0.6.2`）。
- **字幕时机不冒充精度**：15 秒粗窗 ASR 与估算时间绝不冒充逐词精校字幕。
- **必保画面与原声前置把关**：Agent 在 `clip_plan.json` 的 `required_evidence` 中声明决不能剪丢的关键问答与反应，工具在完成边界吸附后、正式渲染前逐条核验。
- **直接扫描真实成片切点**：`shot_review.py` 直接解码渲染出的视频文件排查碎镜头，而不是只看计划表上的片段长度；同时明确记录“零候选不等于无闪帧”。
- **终审质检支持严格阻断（`--require-final-qc`）**：显式开启后，只要 `final_qc.json` 存在任何阻断项，命令即以非零退出码报错停机。

与此同时，语义与叙事层面的要求——解说词是否有画面与原声证据支撑、有没有脑补未发生的情节、有没有挤占本该留给原声的拍（`validate.py` 只核对与对白的时间重叠，不读 `visual_audio_board.json`）、开场承诺是否兑现、有没有公文套话（确定性校验只拦示例占位符泄漏）——不设模型打分门禁，完全依靠 `video-recap` 中的 Agent 自检与交付前原速看片把关；切勿把 `validate.py` 通过等同于叙事品质达标。

## 警钟长鸣的五个典型反例

- **技术全绿但故事断链**：把铺垫起因的镜头剪丢了，哪怕帧率、响度、句界全部合格，观众照样看不懂后面为什么突然翻脸。
- **粗窗转写冒充精对位**：15 秒一窗的 ASR 能把台词全转出来，但人物实际开口可能在窗口第 6 秒；直接按字数均分打字幕必定声画不同步。
- **缓存更新但混音吃旧件**：新跑的 TTS 写进了缓存，但混音脚本读的仍是旧目录里的 WAV；只查 `tts_meta.json` 根本发现不了成片声音没变。
- **长区间里藏着碎反打**：EDL 计划里写的是连续 12 秒，但原片在这 12 秒中间切了一个几帧的废镜头；光查计划表段长必定漏检。
- **改了计划还没重渲就交差**：只改了 `clip_plan.json` 却没重跑渲染，拿工作目录里上一轮留下的旧 `output.mp4` 当新成片交付。

## 双层回归验证体系

1. **第一层（确定性重建与规格核验）**：给定源片与旁白文稿，重建画面、字幕与包装，逐项核对镜头顺序、输出总帧数、字幕切入帧、实际字号坐标与尾段收束。不同平台的编码器存在细微差异，不强求整段 MP4 逐字节完全相同。
2. **第二层（盲测端到端审查）**：只给源视频、创作要求与返修意见，不给标准答案，跑完后用独立维护的盲测问题集逐项核查。盲测题库与具体商业项目的映射关系仅保存在私有基准库中，绝不写进开源通用分支。
